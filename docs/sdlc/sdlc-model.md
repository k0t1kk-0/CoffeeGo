# Вибір моделі SDLC

## Картка проєкту

| Поле | Значення |
|---|---|
| Назва проєкту | CoffeeGo — мобільний застосунок попереднього замовлення кави |
| Тип системи | Mobile (iOS, Android) + Web (панелі бариста і менеджера) + API |

## Оцінка за критеріями

| Критерій проєкту | Відповідь для CoffeeGo | Модель SDLC | Метод |
|---|---|---|---|
| Вимоги стабільні, замовник — держустанова або тендер | Ні: замовник комерційний, вимоги до бонусів змінюються | Waterfall | Структурні |
| Потрібна формальна верифікація (критична система) | Ні: збій не загрожує життю | V-модель | Формальні |
| Вимоги уточнюються ітераційно, ОО-аналіз | Частково, але команда мала для RUP | Ітераційна (RUP) | Об'єктно-орієнтовані |
| Високі ризики, великий інноваційний проєкт | Ні: проєкт невеликий; ризик — інтеграція з POS | Спіральна | Універсальна |
| Команда невелика, потрібні часті релізи | **Так**: 4 особи, жорсткий строк, щотижневі демонстрації | **Scrum / Kanban** | **Гнучкі (Agile)** |

## Обґрунтування

Обрано **Scrum з тижневими спринтами**, а після релізу — Kanban для супроводу. Команда з чотирьох осіб і строк у п'ять тижнів добре лягають у п'ять коротких спринтів, після кожного з яких замовник бачить робочий інкремент. Вимоги до бонусів і оплати ще уточнюються, тому зміни потрапляють у наступний спринт, а не ламають затверджений план, як у Waterfall. Scrum вимагає менше формальної документації — для комерційного замовника достатньо SRS і Product Backlog. Найбільший ризик — інтеграцію з POS — беремо в перший спринт і перевіряємо на демонстрації вже через тиждень. V-модель і спіральна модель тут надлишкові: система не критична, а проєкт невеликий.
